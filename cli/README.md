# p3k

CLI для пути проекта от пустой папки до продакшена.

- **`init`** — каркас проекта и `p3k.json`, с которого начинается всё остальное.
- **`add`** — добавить ресурс: базу, кэш, хранилище, прокси. Одно описание на локалку и на сервер.
- **`dev`** — поднять окружение одной командой, в правильном порядке, с одним потоком логов и корректной остановкой.
- **`check`** — прогнать проверки проекта до того, как это сделает CI.
- **`ship`** — выкатить на свой сервер: выпуск рядом с работающим, проверка здоровья, откат.
- **`doctor`** — выяснить, почему оно не поднимается.

Связывает их конфиг: `init` его пишет, `add` дополняет, `dev`, `check` и `ship`
читают. Одно описание ресурса даёт и контейнер на ноутбуке, и службу на сервере
— в этом вся идея.

Рантайм-зависимостей нет. Нужен Node 18+.

```bash
npm install
npm run build
npm test

node dist/cli.js init мой-проект --template static
node dist/cli.js add postgres
node dist/cli.js dev
node dist/cli.js check
node dist/cli.js ship --dry-run
node dist/cli.js doctor
```

## init

```
$ p3k init my-site --template static

  Статический сайт → /tmp/my-site

  + package.json
  + build.mjs
  + server.mjs
  + public/index.html
  + p3k.json
  + .env.example
  + .gitignore

  создан git-репозиторий

  Дальше:
    cd my-site
    p3k dev
    откройте http://localhost:4000
```

Шаблоны (`--list`):

| id | что это | нужно |
|---|---|---|
| `static` | сборка и сервер статики — два процесса, показывает одноразовый шаг | — |
| `node-postgres` | база в контейнере, миграции, API — весь граф целиком | Docker |

Смысл команды не в раскладывании файлов, а в том, что она **порождает конфиг**:
шаблон описывает не только исходники, но и то, из чего проект состоит и что от
чего зависит. Дальше этот файл читает `dev`.

### Осторожность с файлами

Непустой каталог — повод остановиться, а не «аккуратно дополнить»: без `--force`
команда откажется работать. Но и с `--force` **существующий файл не
перезаписывается никогда** — он пропускается, и пропуск виден в отчёте.
Перезапись чужой работы необратима, а дописать файл руками легко.

Опции: `--template <id>`, `--name <имя>`, `--list`, `--force`, `--no-git`,
`--help`. Без `--template` в интерактивном терминале спросим, в
неинтерактивном — откажемся с перечнем шаблонов.

## add

```
$ p3k add postgres

  PostgreSQL 16 → postgres

  + p3k.json → processes.postgres
  + p3k.json → resources.postgres
  ~ p3k.json → processes.api: needs, env
  ~ .env.example: DATABASE_URL

  Контейнер: shop-postgres
  Порт 5432 — подключение к базе

  Привязан к процессу "api": он ждёт готовности и получает DATABASE_URL.
```

Ресурс — кусок окружения, который проекту нужен, но который он не пишет сам.
Команда добавляет его в конфиг сразу в двух видах: запись в `processes` для
локальной разработки и запись в `resources`, по которой `ship` соберёт для
сервера `compose.yml`. Источник один, поэтому прод не расходится с локалкой.

| Ресурс | Что это |
|---|---|
| `postgres` | PostgreSQL 16, готовность по `pg_isready`, данные в томе |
| `mysql` | MySQL 8, готовность по `mysqladmin ping` |
| `redis` | Redis 7, локально без тома — кэш одноразовый |
| `mailpit` | ловушка для писем: почта видна в браузере и наружу не уходит |
| `minio` | хранилище файлов с тем же API, что у S3 |
| `nginx` | один адрес на фронтенд и API, `nginx.dev.conf` рядом |

### Что здесь важного

**Привязка.** Команда находит процесс приложения — единственный долгоживущий
процесс, который не является ресурсом, — добавляет ресурс в его `needs` и
кладёт ему адрес подключения в `env`. Приложение после этого стартует не
раньше, чем база начнёт отвечать. Кандидатов несколько — не угадываем, просим
`--link`.

**Чужие значения не трогаются.** Свой `DATABASE_URL` останется вашим; в отчёте
будет сказано, что его оставили как был. То же с файлами: существующий
`nginx.dev.conf` не перезаписывается.

**Порты проверяются дважды** — по конфигу проекта и по тому, что слушает машина
прямо сейчас. Занятый порт даёт отказ с именем процесса-владельца и готовой
командой с другим номером. Порты, по которым ресурс только *ходит* (апстримы
прокси), конфликтом не считаются.

**Пароли локальных контейнеров намеренно простые.** Это `localhost` на полчаса.
Секреты продакшена в конфиг не попадают вообще — их читает `ship` из файла на
сервере.

### Опции

```
--name <имя>       имя процесса (по умолчанию — имя ресурса)
--port <n|id=n>    занять другой порт; можно повторять
--link <процесс>   к какому процессу привязать
--no-link          не привязывать
--dry-run          показать, что изменится, и ничего не записать
--force            добавить, даже если порт занят на этой машине
--list             список ресурсов
```

## dev

Процессы описываются в `p3k.json`:

```json
{
  "processes": {
    "db": {
      "command": "docker run --rm --name pg-dev -p 5432:5432 -e POSTGRES_PASSWORD=dev postgres:16",
      "ready": { "port": 5432 },
      "stop": "docker stop pg-dev"
    },
    "migrate": {
      "command": "npm run migrate",
      "needs": ["db"],
      "oneShot": true
    },
    "api": {
      "command": "npm run dev",
      "cwd": "api",
      "env": { "PORT": "4000" },
      "needs": ["migrate"],
      "ready": { "port": 4000 }
    },
    "web": {
      "command": "npm run dev",
      "needs": ["api"],
      "ready": { "log": "ready in" }
    }
  }
}
```

Вывод:

```
        │ конфиг: /project/p3k.json
        │ процессов: 4, волн запуска: 4
        │ db: запуск — docker run --rm --name pg-dev …
        │ db: готов (порт 5432)
        │ migrate: запуск — npm run migrate
migrate │ применено 2 миграции
        │ migrate: выполнен
        │ api: запуск — npm run dev
api     │ listening on 4000
        │ api: готов (порт 4000)
web     │ ready in 312 ms
        │ всё поднято — Ctrl+C для остановки
```

### Что здесь важного

**Порядок с гарантией.** `needs` задаёт зависимости, процессы стартуют волнами:
внутри волны параллельно, следующая волна — только когда вся предыдущая
**отвечает**, а не «запущена». Ждать умеет три вещи:

| `ready` | когда готов | для чего |
|---|---|---|
| `{ "port": 5432 }` | порт принимает соединение | быстро, но см. ниже |
| `{ "exec": "docker exec pg pg_isready" }` | команда вернула 0 | базы данных |
| `{ "http": "http://localhost:4000/health" }` | ответ со статусом < 500 | HTTP-службы |
| `{ "log": "ready in" }` | строка появилась в выводе | сборщики, воркеры |
| `{ "delay": 800 }` | просто пауза | когда другого способа нет |

**`port` врёт на службах, которые открывают порт раньше, чем готовы
обслуживать.** Postgres принимает соединения ещё во время инициализации
кластера: `{ "port": 5432 }` сработает сразу, зависимый процесс стартует и
получит отказ уже от самой базы. Для баз честен только `exec`, для HTTP —
`http`. Ожидание порта проверяется соединением, а если оно заблокировано
локальной политикой — по таблице слушающих сокетов. Без `ready` процесс
считается готовым сразу.

**Одноразовые задачи.** `"oneShot": true` — процесс должен отработать и выйти
(миграции, кодогенерация). Его готовность — успешный выход, и его завершение
не считается поводом гасить окружение. Без этого флага любой завершившийся
процесс роняет всю сессию, потому что работать без части системы бессмысленно.

**Остановка снимает дерево, а не оболочку.** `command` исполняется через shell,
то есть прямой потомок — это `cmd.exe` или `sh`, а работа идёт во внуках. Убить
одного потомка недостаточно: именно так после Ctrl+C остаются висеть занятые
порты и контейнеры. `dev` гасит всю группу процессов в порядке, обратном
зависимостям, а для того, что переживает смерть родителя, есть `stop`.

**Порты проверяются до запуска.** Занятый порт даёт внятную строку сразу, а не
невнятную ошибку изнутри чужого процесса через десять секунд.

### Опции

`--only <имя>` запустить только этот процесс и то, от чего он зависит (можно
повторять). `--help` справка.

Код возврата: код упавшего процесса, `2` при ошибке конфигурации, `0` при
штатной остановке.

## check

Те же проверки, что потом прогонит CI, но у вас на машине и до пуша.
Проверка — это либо команда, которая должна завершиться успешно, либо бюджет
размера собранных файлов.

```
$ p3k check

  /project/p3k.json

  ✓  types · 2.3с
  ✓  build · 1.5с
  ✓  bundle — 40.0kb из 60.0kb (gzip) · 0.0с

  3 из 3 · 2.3с
```

```json
"checks": {
  "types":  { "command": "npm run typecheck" },
  "build":  { "command": "npm run build" },
  "bundle": { "size": { "path": "dist/assets", "max": "60kb", "gzip": true }, "needs": ["build"] },
  "lint":   { "command": "npm run lint", "optional": true }
}
```

### Что здесь важного

**Параллельно, но в предсказуемом порядке.** Проверки запускаются все сразу, а
печатаются в порядке конфига — вывод одинаков от прогона к прогону, но ждать
приходится по самой медленной, а не по сумме всех. В примере выше 2,3с против
3,8с последовательно.

**`needs` — как в dev.** Поле говорит, какие проверки должны пройти раньше этой.
Бюджет размера считает файлы в `dist`, а создаёт их сборка: без `needs` он
померял бы прошлую сборку или пустой каталог. Проверки идут волнами; если то, от
чего они зависят, не прошло, зависимые помечаются пропущенными, а не
проваленными. Это разные вещи: проваленная значит «проверили, и плохо»,
пропущенная — «проверить не смогли».

**Вывод показывается только у непрошедших.** Логи параллельных проверок
вперемешку нечитаемы, поэтому они копятся и печатаются только там, где что-то
сломалось.

**Бюджет размера** считает файл или каталог целиком; `"gzip": true` сжимает
каждый файл отдельно и складывает — так же, как их отдаст сервер. При
превышении печатаются пять самых крупных файлов: это то, с чем идти разбираться.

**Без секции `checks`** проверки выводятся из `scripts` в package.json
(`typecheck`, `types`, `lint`, `test` — от быстрых к медленным). `build` туда
намеренно не входит: у него побочные эффекты. Источник всегда напечатан первой
строкой.

**Кэш по содержимому входов.** Поле `inputs` перечисляет файлы и каталоги, от
которых зависит результат; пока они не менялись, успешный результат берётся из
кэша, а проверка не запускается. Ключ считается по содержимому, а не по `mtime`:
после `git checkout` время меняется, а содержимое нет, и кэш по времени
сбрасывался бы впустую. Сама команда тоже входит в ключ.

```json
"types": { "command": "npm run typecheck", "inputs": ["src", "tsconfig.json"] }
```

Запоминается только успех: причина провала часто лежит вне объявленных входов —
сеть, чужой процесс, занятый порт. Без `inputs` проверка не кэшируется вовсе.
Кэш лежит в `node_modules/.cache/p3k/`, сбрасывается флагом `--no-cache`.

Опции: `--only <имя>` (подтягивает то, от чего проверка зависит), `--list`,
`--no-cache`, `--json`, `--help`. Код возврата `1`, если не прошли обязательные проверки, `2`
при ошибке конфигурации.

## ship

```
$ p3k ship

  root@203.0.113.10 · /srv/shop
  выпуск 20260907-104233 · сейчас работает 20260906-183001

  ✓  types 4.5с · test 12.1с · 2 из 2
  ✓  собрано за 6.7 с
  ✓  отправлено за 1.9 с: dist, package.json, package-lock.json
  ✓  службы подняты: postgres
  ✓  выполнено за 8.3 с
  ✓  current → 20260907-104233, служба перезапущена
  ✓  здоров за 3.1 с (https://ваш-домен/health → 200)

  выкачено: 20260907-104233
  откатиться: p3k ship --rollback  →  20260906-183001
```

Выкатка ничего не хостит. Она управляет вашим сервером по SSH: новый выпуск
заливается **рядом** с работающим, и только после того, как всё готово, ссылка
`current` переключается на него. Поэтому откат — это движение ссылки обратно, а
не повторная сборка.

```
/srv/shop/
  releases/
    20260907-104233/   новый выпуск
    20260906-183001/   прежний, нетронутый
  shared/
    .env               секреты, остаются на сервере
    compose.yml        собран из resources
  current -> releases/20260907-104233
```

### Порядок шагов

| Шаг | Что происходит |
|---|---|
| проверки | сначала `check` — не прошли, выкатка не начинается |
| сборка | локально, командой `build` |
| отправка | `upload` едет в новый каталог выпуска |
| службы | `compose up -d --wait` поднимает базу и кэш |
| в выпуске | `release`: зависимости, миграции — **до** переключения |
| переключение | `current` меняется одним `mv`, затем `restart` |
| здоровье | опрос `health`, пока приложение поднимается |
| откат | не ответило — `current` возвращается на прежний выпуск |

### Что здесь важного

**Секреты остаются на сервере.** Пароли лежат в `shared/.env`, который вы
заполняете один раз сами; в `compose.yml` попадают только ссылки вида
`${POSTGRES_PASSWORD:?…}`, а в `p3k.json` — ничего. Первая выкатка без этого
файла честно откажется идти дальше и положит рядом `.env.example` со списком
переменных.

**Порты служб в проде выставлены только на петлю** (`127.0.0.1:5432:5432`).
Исключение одно — `nginx`, который и должен смотреть наружу.

**Переключение — одно движение.** `ln -sfn` сначала удаляет ссылку, и в этот
промежуток сайт отвечал бы ошибкой; поэтому ссылка создаётся под временным
именем и переносится через `mv -Tf`.

**Провал до переключения ничего не ломает.** Упавшая миграция оставляет
работать прежний выпуск, а негодный остаётся на диске — с ним можно разобраться
не торопясь.

**`health` опрашивается с той машины, откуда идёт выкатка**, а не с сервера.
Значит, там должен стоять публичный адрес приложения.

**ssh идёт в режиме `BatchMode`** — без пароля. Нужен ключ: проверьте, что
`ssh <хост> true` отрабатывает молча. Спросить пароль не у кого — вывод
перехвачен, и команда просто зависла бы.

### Опции

```
--to <user@host>  цель поверх той, что в конфиге
--dry-run         показать план и проверить связь, ничего не меняя
--skip-checks     не прогонять check
--no-rollback     не откатываться при неудачной проверке здоровья
--rollback        вернуться на предыдущий выпуск и выйти
--releases        показать выпуски на цели
```

Цель без `host` — эта же машина: каталог вместо сервера. Так проверяется вся
логика выпусков и отката, и на этом же держится автотест выкатки.

## doctor

Обычный dev-сервер при сбое печатает ошибку того слоя, где сломалось. Проблема
в том, что самые частые сбои **не дают ошибки вовсе** — или дают такую, которая
уводит не туда. `doctor` проверяет окружение напрямую и печатает, что именно
сломано и какой командой это чинится.

```
  СЕТЬ
  ✗  3000 слушается только по IPv6
     привязка: ::1 — этот адрес не принимает IPv4-соединения
     localhost резолвится в ::1, 127.0.0.1
     браузеры и curl, выбирающие IPv4, получат отказ: страница будет пустой,
     а в логе сервера не появится ни одной ошибки
     → привяжите сервер к IPv4: server.host = '127.0.0.1' в конфиге
```

| Группа | Что смотрит |
|---|---|
| РАНТАЙМЫ | версия Node против `engines.node`; демон Docker — только если в проекте есть Dockerfile или compose |
| ПОРТЫ | занят ли порт и каким процессом (PID и имя) |
| СЕТЬ | резолвится ли `localhost`; доступен ли слушающий порт и по IPv4, и по IPv6 |
| ОКРУЖЕНИЕ | ключи из `.env.example`, которых нет ни в `.env`, ни в окружении процесса |
| ЗАВИСИМОСТИ | установлен ли `node_modules` и не отстал ли от локфайла; нарушенные peer-зависимости |

Порты берутся из `scripts` в package.json и из конфигов (`vite.config.*` и
подобных). Конфиги читаются **текстом, а не исполняются**: запускать чужой код
ради номера порта — плохой размен. Поэтому у каждого порта указан источник.

Опции: `--port <n>`, `--json`, `--help`. Код возврата `1` при блокирующих
проблемах — годится для CI и pre-commit.

### Три правила, по которым отбираются проверки

1. **Детерминированный сигнал.** Не эвристика, а факт: сокет либо слушает
   адрес, либо нет.
2. **Готовое действие.** Конкретная команда или правка, а не «проверьте
   настройки сети».
3. **Реальная частота.** Иначе это шум, в котором тонет полезное.

Отсюда четвёртое — **честность о границах**. Проверка, которая ничего не
выяснила, обязана сказать «не выяснил», а не «всё хорошо» и не «всё сломано».
Заблокированная фаерволом проба соединения — это отсутствие данных, а не
закрытый порт. Всё пропущенное перечисляется отдельной строкой в конце отчёта.

## Устройство

```
src/
  cli.ts          диспетчер команд
  types.ts        общие типы
  util/           exec, net, semver, project, plural — общее для всех команд
  config.ts       поиск и чтение p3k.json — общее для dev и check
  init/           index (аргументы и запись файлов), templates (шаблоны)
  dev/            index (аргументы), config, graph, supervisor, log
  add/            resources (каталог ресурсов), plan (правка конфига), index
  ship/           config (секция deploy), target (SSH и локальная цель),
                  compose (сборка продакшен-манифеста), index (порядок шагов)
  check/          index (прогон и вывод), config (проверки), size, cache
test/             тесты на чистые функции: node:test, без зависимостей
  doctor/         index (сбор отчёта), report (вывод), checks/*
```

Проверка доктора — объект `{ id, group, run(ctx) }`; упавшая проверка не роняет
отчёт, а превращается в `skip` с текстом ошибки. Добавить новую — один файл в
`src/doctor/checks/` и строка в массиве в `src/doctor/index.ts`.

Планировщик волн (`util/graph.ts`) общий: `dev` раскладывает по нему процессы,
`check` — проверки. Задача одна и та же, и решать её дважды незачем.

Разбор диапазонов версий свой, ~130 строк, без зависимости от `semver`: умеет
`^ ~ >= > <= <`, неполные версии (`>=18`), `1.2.x`, `||` и пересечения. Всё, что
разобрать не удалось, даёт «не знаю», а не «не подходит».

## Тесты

```bash
npm test    # tsc -p tsconfig.test.json && node --test .test-build/test/
```

79 тестов на `node:test` — встроенный раннер, зависимостей не добавляет.
Покрыты чистые функции, где ошибка тихая и дорогая: разбор диапазонов версий,
планировщик волн, измерение размеров, разбор всех конфигов, ключ кэша, план
добавления ресурса и сборка compose.

Два теста сложнее: каталог ресурсов прогоняется через настоящий разбор
конфига `dev` (ошибка в данных иначе всплыла бы только у пользователя), а
выкатка проверяется целиком на локальной цели — с поднятым HTTP-сервером,
испорченным выпуском и откатом на прежний.

## Известные ограничения

**Конфиг `dev` — JSON, а не TypeScript.** Исполнять пользовательский TS
пришлось бы через сборщик: зависимость и целый класс ошибок ради удобства
записи. TS-конфиг возможен позже, отдельным шагом.

**Осиротевшие процессы при жёстком убийстве родителя.** Если сам `p3k dev`
снят через SIGKILL или `taskkill /F`, обработчик не отработает и дети выживут.
Надёжное решение на Windows — job object с `KILL_ON_JOB_CLOSE`, а это нативный
модуль, то есть зависимость. Штатный путь остановки (Ctrl+C, падение процесса)
дерево снимает полностью.

**Мягкая остановка на Windows почти всегда не срабатывает.** `taskkill` без
`/F` шлёт `WM_CLOSE`, который консольные приложения игнорируют, поэтому там
пауза перед принудительным снятием короткая — растягивать её значит просто
задерживать выход.

**`check` не умеет диффа миграций** — он есть в замысле, но требует поднятой
базы и разбора схемы. Пока это описывается обычной проверкой вида `command`.

**Контейнеры оркестрируются через обычный `command`**, а не через docker API:
`docker run …` плюс `stop`. Отдельного вида `service` пока нет.

**Unix-ветка определения владельца порта** (`lsof`, с откатом на `ss`) написана,
но на живой системе не проверялась — тестовая машина под Windows.

**Выкатка по SSH на живом сервере не проверялась.** Проверены: вся логика
выпусков, переключения, здоровья и отката — на локальной цели; сборка
`compose.yml` и подъём служб — настоящим `docker compose` на этой машине.
Ветка SSH (`ssh`, `tar` через конвейер, `ln`/`mv` на удалённой стороне) написана
и разобрана тестами, но на чужой машине не запускалась. Первую выкатку делайте
с `--dry-run`.

**Двух версий рядом нет.** Переключение мгновенное, но одномоментное: канарейка
и постепенный перевод трафика — замысел, а не возможность.

**TLS не выпускается.** `nginx` поднимается без сертификатов; за ними идите к
certbot.

**Шаблон `node-postgres` целиком не прогонялся.** Проверено, что `init` его
раскладывает и что `dev` разбирает порождённый конфиг в правильные волны
(`db` → `migrate` → `api`). Зато все шесть ресурсов из `add` подняты
по-настоящему и дождались своих условий готовности, а `dev` прогнан целиком на
связке postgres + redis + приложение, включая остановку без осиротевших
контейнеров.

**Шаблоны — это файлы, а не запуск чужих скаффолдеров.** Делегирование вида
`npm create vite@latest` в план заложено, но в этой версии его нет: оно требует
сети и делает результат непроверяемым.

**Имя проекта приводится к безопасному виду** (латиница, цифры, дефис) — оно
попадает в `package.json` и в имя контейнера. Если пришлось что-то заменить,
команда об этом скажет.
