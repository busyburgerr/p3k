# p3k

CLI для пути проекта от пустой папки до продакшена — и сайт про него.

**`p3k init`** раскладывает каркас и пишет конфиг. **`p3k add`** добавляет
проекту ресурс — базу, кэш, хранилище, прокси — одним описанием сразу для
ноутбука и для сервера. **`p3k dev`** поднимает это локально и ждёт, пока
каждый кусок начнёт отвечать. **`p3k check`** прогоняет те же проверки, что
потом прогонит CI. **`p3k ship`** выкатывает на ваш VPS: выпуск рядом с
работающим, проверка здоровья, откат переключением ссылки. **`p3k doctor`**
объясняет, почему что-то из этого не поднялось.

Рантайм-зависимостей нет. Нужен Node 18 или новее.

```bash
npm i -g @busyburger/p3k

p3k init мой-сервис --template node-postgres
cd мой-сервис
p3k add redis
p3k dev
```

## Идея

Одно описание ресурса даёт два окружения. `p3k add postgres` пишет в конфиг
и запись в `processes` — контейнер, который поднимет `dev` на вашей машине, —
и запись в `resources`, по которой `ship` соберёт для сервера `compose.yml`.
Прод не расходится с локалкой не потому, что кто-то аккуратно переписал конфиг
дважды, а потому что источник один.

Секреты продакшена в конфиг не попадают: они лежат в `shared/.env` на самом
сервере, а в манифест уходят только ссылки на переменные.

## Что в репозитории

| Каталог | Что это |
|---|---|
| [`cli/`](cli) | сам инструмент — шесть команд, 79 тестов, ноль зависимостей |
| [`go/`](go) | то же самое библиотекой для Go: окружение поднимается внутри вашей программы |

| [`starter/`](starter) | заготовка сайта на том же каркасе — копируется под новый проект |

Пакет публикуется из `cli/`. Подробная документация по командам и конфигу —
в [cli/README.md](cli/README.md) и на страницах сайта.

## Библиотека для Go

Тот же конфиг, те же правила, но окружение поднимается внутри вашей программы —
и его можно дождаться, прочитать и погасить:

```go
env := p3k.New(cfg, p3k.WithOnly("postgres", "redis"))
if err := env.Start(ctx); err != nil { log.Fatal(err) }
defer env.Stop(ctx)
```

Пригодится интеграционным тестам, которым нужны настоящие база и кэш. `Start`
возвращается, когда база начала отвечать, а не когда контейнер запущен.
Подробности — в [go/README.md](go/README.md).

Там же решена задача, которую Node-версия решить не может без нативного
модуля: на Windows дерево процессов гасится ядром, даже если саму программу
сняли принудительно.

## Запуск

```bash
# инструмент
cd cli && npm install && npm run build && npm test

# библиотека для Go
cd go && go test ./...

# сайт
npm install && npm run dev        # http://127.0.0.1:3000

# заготовка
cd starter && npm install && npm run dev
```

Сайт сам является потребителем инструмента: в корне лежит [`p3k.json`](p3k.json),
поэтому `node cli/dist/cli.js dev` поднимает его, а `check` прогоняет типы,
сборку, бюджет размера бандла и разбор рецептов с сайта настоящими парсерами CLI.

## Состояние

Версия 0.2, ранняя разработка, пользователей пока нет. Написаны и работают шесть
команд. Проверено вживую: все шесть ресурсов подняты настоящими контейнерами и
дождались своих условий готовности; `dev` прогнан целиком на связке
postgres + redis + приложение, включая остановку без осиротевших контейнеров;
`ship` проверен на локальной цели — с испорченным выпуском и откатом на прежний
— и на настоящем `docker compose`.

Не проверено вживую: выкатка по SSH на чужом сервере, определение владельца
порта на Unix. Чего нет вовсе — двух версий рядом, канарейки, TLS,
превью-окружений на PR — перечислено в разделе «Границы» документации и в
[известных ограничениях](cli/README.md).

Сборка и тесты идут на Linux, macOS и Windows под Node 18, 20 и 22. Ручные
прогоны шли под Windows.
